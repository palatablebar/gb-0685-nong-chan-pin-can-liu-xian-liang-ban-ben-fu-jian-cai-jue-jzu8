# 检测区间与复检

采样日期选择限量标准[start,end)，不使用报告出具日。同产品同残留项目在采样日须恰有一条有效标准，方法须在适用范围内。浓度统一mg/kg，ug/kg与ppb乘0.001，ppm等于mg/kg。检出限LOD必须大于0。

定量值以[value,value]记录，低于LOD的定量值拒绝。ND或<LOD以[0,LOD)记录，<后的数值必须等于报告LOD。区间上界≤限量为PASS，下界>限量为FAIL，其余UNCERTAIN。<0.01相对0.005限量为不确定，不能当零。

复检relation指向原报告，必须同样本、同批次、同产品、同残留项目、同方法、同采样日，报告日严格更晚。引用环、悬空引用与异样本引用隔离。每样本/项目只允许一个原始报告根。有效复检按reported、version取最新；并列结果矛盾拒绝。其他残留项目不因复检被覆盖。批次按FAIL>UNCERTAIN>PASS取最高风险等级。

## 通用采信约定

CSV按UTF-8 BOM、UTF-8、GB18030回退，保留逻辑记录结束行号；引号内换行由CSV解析。重复表头单独计数，列数不齐隔离。编码与ID按字符串保形。缺失哨兵为 `-`、`N/A`、`NULL`、`未知` 与空串；不得作为零。数值先NFKC归一、去千分位，再用Decimal。日期采用ISO；时间必须带偏移并转UTC。空文件、全空行、仅表头分别返回EMPTY_FILE、BLANK_FILE、HEADER_ONLY。

重复键为(id,version)，完全相同行去重；同键内容冲突则整组隔离，不取最后一行。行数对账：输入=采纳+隔离+空行+重复表头+完全重复。运行幂等键由输入字节、参数与规则版本计算。

同一报告ID的多个版本先选最高version，再构建复检引用链；历史版本留作采信证据，不重复参与最终项目判定。

## 制备基准与可食部浓度依据

外检报告可能按全果基出具、按可食部基出具，或未注明制备基准；内控限量一律按可食部基。每份报告单独推导浓度依据，**绝不按批次统一套用比例**：

- `basis` 列（别名 `prep_basis`、`制备基准`、`可食部基准`、`浓度基准`、`检测基准`）取值归一为 `可食部`、`全果`、`未注明`。
- 可食部基：比例必须为 1，直接判定。
- 报告自带 `edible_ratio` 列（别名 `可食部比例`）时，视为该报告自带的比例凭据，仅对该报告生效；比例 `<1` 按全果基换算，`=1` 按可食部基。同批其他报告不会套用该比例。
- 全果基：必须取得该样本（或该报告）的可食部比例凭据 `r∈(0,1]`，可食部基浓度 = 全果基浓度 ÷ r，判定边界按可食部基限量比较。比例凭据缺失时该项目**待补录**，不得发布。
- 未注明基准：等待比例凭据；凭据声明全果基时按全果基换算，声明可食部基时按可食部基判定。无凭据时待补录，不得按批次默认值猜测。
- 仅当报告**没有基准列、且输入完全没有任何比例凭据**时，旧版报告延续历史默认可食部基（`legacy_default`），并在归档中显式标注。
- 比例凭据字段：`sample_id` 或 `report_id`（至少一个）、`batch`、`product`、`basis`、`edible_ratio`、`version`、`source`、`note`。可同时给 `report_id` 与 `sample_id`；`report_id` 优先。
- 同一凭据 `(report_id, sample_id, product, batch, version)` 内容冲突时整组拒绝（`EVIDENCE_CONFLICT`）；重复相同凭据去重，不新增项目。
- 报告声明可食部基但凭据为全果基（或反之）判 `BASIS_CONFLICT` 并隔离。

### 发布与挂起

复检裁决按样本/项目分组：最新报告缺少可食部依据时，该项目整体进入 `held`（原因 `RATIO_MISSING` 或 `BASIS_MISSING`），旧报告不能抢先发布；其他有依据的项目照常发布并计入 `business`。`reconcile.held` 记录挂起项目数。

### 封存资格

`reconcile.sealable` 与 `archive.ready` 要求：对账平、无挂起项目、全部已发布项目的 `concentration_basis` 均为可食部。批次级 `code`、`held`、`sealable` 与项目结果共用同一条可食部浓度依据。未具备封存资格时导出返回 `NOT_SEALABLE`。

### 补录、恢复与幂等

- `POST /api/runs/<id>/evidence` 补录比例凭据，沿用同一份原始报告字节形成新裁决版本；补录失败（校验不通过）不落库，当前批次与原结论保持不变。
- `POST /api/runs/<id>/restore` 恢复上一版批次结果（补录失败或人工退回）。
- 同一来源（原始报告字节相同）重跑时进入同一 `source_id`，同一 `run_id` 不新增记录、不重复增加项目，已确认（`通过`）且结论一致的复核状态保留。
- 已确认的结论不得被新版本改动或减少（`CONFIRMED`），需先退回。

### 留档

归档 CSV 记录类型新增 `裁决版本`、`原始报告`、`待补录`、`凭据原文`；`原始报告` 保存报告字节的 base64、编码与 sha256；`凭据原文` 保存比例凭据字节的 base64、编码与 sha256，运行清单保存原始报告 sha256 与参数，原始报告字节保存在运行记录的 `source_b64`，避免证据数据丢失。
